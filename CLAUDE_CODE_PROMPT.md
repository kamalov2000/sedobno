## Контекст
- Проект: Telegram mini-app «сканер состава» — фото этикетки → оценка 0–100 + красные флаги. Детали в SPEC.md.
- Я Go-разработчик, ревью буду делать по Go-коду строго.
- Инфраструктура: Docker Compose, деплой на Ubuntu VPS (Timeweb). Postgres в контейнере.
- Секреты: только env, fail-fast при отсутствии обязательной переменной на старте приложения (паника с внятным сообщением). Пример: TELEGRAM_BOT_TOKEN, LLM_PROVIDER, GROQ_API_KEY, DATABASE_URL, JWT_SECRET, ADMIN_KEY, SUBSCRIPTION_STARS_PRICE.
- Никаких хардкод-токенов нигде, включая тесты и докер-файлы. .env.example — обязателен.

## Технические решения (не обсуждаются, если не найдёшь блокер)
- Backend: Go 1.22+, роутер chi, sqlc или чистый pgx для Postgres (без тяжёлых ORM), миграции goose или migrate.
- Frontend: Vite + React + TypeScript + Tailwind, статика раздаётся из контейнера web (nginx) или из api — выбери проще. Telegram WebApp SDK (@twa-dev/sdk или официальный script).
- LLM: интерфейс `LLMProvider` (методы ExtractIngredients(image) и MatchIngredients/Explain(text)) c реализациями groq и openai-совместимой запасной. Выбор через env LLM_PROVIDER. Строгий JSON-выход (json mode / схема в промпте + валидация + один retry при невалидном JSON).
- Скоринг: детерминированный, в Go, правила из SPEC.md §5, коэффициенты в конфиг-файле (yaml или таблица), не в коде.
- Тесты: юнит-тесты на скоринг (табличные) и на матчер словаря — обязательны. На HTTP-хендлеры — базовые happy-path.

## Этапы

### Этап 0 — скелет
Монорепо: /api (Go), /web (фронт), /deploy (docker-compose.yml, Caddyfile или nginx.conf), Makefile (build, up, migrate, test, evalpipe). Healthcheck GET /api/health. Postgres поднимается, миграции применяются.
Приёмка: `make up` → все контейнеры зелёные, /api/health отвечает.

### Этап 1 — словарь
Миграции всех таблиц из SPEC.md §7. Сид словаря: сгенерируй ~250–300 E-добавок + ~20 не-E маркеров по схеме §6 (users увидят verdict-тексты — пиши их по-русски, спокойным тоном, без медицинских утверждений; для спорных веществ формулировка «спорный/ограниченно допустимый»). Сид — отдельный файл data/additives_seed.json + загрузчик. Пометь в sources_note основание оценки. В конце этапа выдай мне список топ-50 самых распространённых добавок из сида отдельным файлом REVIEW_TOP50.md — я проверю формулировки руками.
Приёмка: `make migrate && make seed` → в БД ~270+ записей, юнит-тест матчера синонимов зелёный.

### Этап 2 — пайплайн + тест-харнесс
Реализуй 4 фазы пайплайна из SPEC.md §4 и CLI `cmd/evalpipe` из §12. Промпты для vision/LLM храни в /api/prompts/*.txt (не в коде), с версионированием в имени файла.
Приёмка: кладу 5 своих фото в testdata/labels, `make evalpipe` выдаёт таблицу с score, стоимостью и латентностью по каждому файлу.

### Этап 3 — API
Все эндпоинты из SPEC.md §8: auth c валидацией initData (реализуй HMAC-проверку по официальной доке Telegram, покрой тестом с известным вектором), scan с лимитами и списанием только при успехе, me, admin/stats. Rate limit 5 сканов/мин.
Приёмка: curl-сценарий в docs/api_examples.md проходит: auth → 10 сканов → 11-й возвращает 402/paywall-ответ.

### Этап 4 — mini-app
Дизайн уже импортирован (см. раздел «Дизайн уже готов» в начале документа) — не вайрфреймь заново. Перенеси разметку и токены из `Съедобно - экраны.dc.html` на стек: три экрана из SPEC.md §3 (главный, результат, пейволл) + лоадер и ошибка. Состояния: лоадер скана (5–8 сек, три фазы, как в дизайн-файле), ошибка «не вижу состав» с подсказками. Дизайн: Telegram themeParams (light/dark), брендовый слой (иконка, хиро-блок пейволла) только там, где он в дизайн-файле — экраны сканирования/результата/лоадера/ошибки нейтральные. Дисклеймер из §11 на экране результата.
Приёмка: открывается в Telegram (через тестового бота и https-туннель или деплой), полный путь фото→результат работает с телефона, визуально соответствует импортированному дизайну в обеих темах.

### Этап 5 — оплата Stars
`/api/pay/create` (subscription invoice, XTR, период 30 дней, цена из env), обработка pre_checkout_query и successful_payment в вебхуке, запись в subscriptions, снятие лимита. Отображение статуса подписки в mini-app. Учти повторную доставку вебхуков (идемпотентность по telegram_charge_id).
Приёмка: тестовая оплата проходит, после оплаты 11-й скан работает, admin/stats показывает revenue.

### Этап 6 — аналитика и деплой
События из SPEC.md §10 пишутся из бэка (не из фронта, где можно — надёжнее). deploy/README.md: пошаговый деплой на VPS (compose, домен, TLS через Caddy/certbot, установка вебхука бота). Логи структурированные (slog), уровень из env.
Приёмка: чеклист деплоя воспроизводим, admin/stats отдаёт все счётчики.
