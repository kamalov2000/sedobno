# Сканер состава — спека MVP (v1.0)

Рабочее кодовое имя: `sostav` (продуктовое имя выбрать до запуска; кандидаты: СоставOK, ЕдаСкан, Чистый Состав).

## 1. Продукт одним предложением

Пользователь фотографирует состав продукта на этикетке → через ~5 секунд получает оценку 0–100, три главных «красных флага» и короткое объяснение простым языком, что в составе плохого и почему.

- **Референс:** Yuka (Франция, 55+ млн пользователей), но без штрихкодов и баз товаров — только фото этикетки + AI. Работает на любом товаре с первого дня.
- **Аудитория первой волны:** мамы, ЗОЖ-аудитория, люди с ограничениями (сахар, аллергии — профили в v1.1, не в MVP).
- **Платформа:** Telegram mini-app. Авторизация — Telegram ID из initData, никаких регистраций.
- **Позиционирование:** «карманный нутрициолог». НЕ медицинский сервис (см. §11).

## 2. Скоуп MVP

**Внутри:**
- Mini-app: 3 экрана (главный, результат, пейволл).
- Загрузка фото (камера/галерея через file input).
- Пайплайн: фото → извлечение состава → нормализация по словарю → детерминированный скоринг → LLM-объяснение.
- Лимит: 10 бесплатных сканов **навсегда** (не в месяц) на telegram_id.
- Подписка через Telegram Stars (месячная, авто-продление средствами Stars subscriptions).
- Серверное сохранение всех сканов (для аналитики; в UI истории нет).
- Событийная аналитика (§10).
- Бот: `/start` → приветствие + кнопка открытия mini-app.

**Снаружи (v1.1+, не строить сейчас):**
- История сканов, избранное, сравнение товаров, «чем заменить».
- Профили (аллергии, ребёнок, сахар).
- Habit-слой: стрики, еженедельный «рейтинг корзины».
- Оплата ЮKassa/СБП на лендинге.
- Приём фото прямо в чат бота (воронка «прислал фото → результат + кнопка в mini-app»).
- Косметика (пивот/расширение: та же механика, другой словарь).

## 3. Пользовательский флоу

1. Пользователь попадает в бота (посев/ролик) → `/start` → кнопка «Проверить продукт».
2. Mini-app, главный экран: большая кнопка «Сфотографировать состав», счётчик оставшихся бесплатных сканов. Подсказка на экране упоминает: если состав не помещается в один кадр (круглая банка/баночка) — можно снять по частям.
3. После первого фото — промежуточный шаг (не отдельный полноэкранный экран, компактная плашка над кнопками): миниатюра сделанного фото + два действия — «Готово, проверить» (отправить на скан) и «+ Добавить ещё фото» (снять следующий ракурс той же этикетки). Максимум 3 фото за один скан. Пользователь решает сам, сколько кадров нужно — большинству хватит одного, круглым упаковкам обычно нужно 2.
4. Фото(-а) → лоадер (5–8 сек) → экран результата:
   - шкала 0–100 с цветом (0–39 красный / 40–69 жёлтый / 70–100 зелёный);
   - до 3 «красных флагов» (худшие ингредиенты) с объяснением в 1–2 предложения каждый;
   - свёрнутый полный список распознанных ингредиентов с бейджами риска; **каждая строка списка разворачивается по тапу и показывает `verdict_full` из словаря (§6)** — то же самое поле, что уже используется для карточек-флагов, просто не было проброшено дальше топ-3. Источник: первый реальный внешний тест (не сотрудник, не разработчик) — пользователь не понимал происхождение бейджей риска у ингредиентов вне топ-3 («цитрат натрия», «ксантановая камедь», «натуральные ароматизаторы») и явно сформулировал запрос «хочу нажать и прочитать, что это такое» + «на фоне чего он делает эти выводы, почему я должна доверять». Это прямой удар по доверию — центральной ценности продукта — поэтому приоритет выше обычного бэклога, несмотря на то что пришло уже в разгар подготовки к запуску;
   - кнопка «Проверить ещё».
5. Скан №11 → пейволл: цена, что даёт подписка (безлимит сканов), кнопка оплаты Stars.
6. После оплаты — безлимит, бейдж подписки на главном экране.

Обработка ошибок фото: «не вижу состав на фото» → подсказка как снять (ближе, при свете, только блок состава) + скан НЕ списывается с лимита, если пайплайн не смог извлечь ингредиенты.

## 4. Архитектура

**Три контейнера (docker-compose):**
1. `api` — Go (стандарт: chi или echo), вся логика: auth, лимиты, пайплайн, платежи, вебхук бота.
2. `web` — mini-app: Next.js (App Router, static export) или Vite+React — на усмотрение исполнителя, критерий: минимум движущихся частей. Tailwind.
3. `postgres` — пользователи, сканы, подписки, словарь.

Реверс-прокси — Caddy или nginx (можно четвёртым контейнером либо использовать существующий на VPS). Деплой — Timeweb VPS, отдельный compose-проект от ClipsGold.

**AI-пайплайн (ключевое решение — двухфазный, скоринг НЕ доверяется LLM):**

- **Фаза 1 — извлечение.** Vision-модель получает **от 1 до 3 фото** одной этикетки (несколько ракурсов — для нецельного кадра на изогнутой упаковке, где состав не помещается в один снимок), все изображения передаются в **одном вызове модели** как отдельные image-блоки одного сообщения — не отдельными вызовами с последующим слиянием текста. Причина: порядок ингредиентов критичен для скоринга (§5 — позиция сахара/соли в первых трёх строках), а склейка текстов из раздельных распознаваний рискует перепутать порядок или задвоить фразы на стыке кадров; модель, видя все фото сразу, сама читает состав как один непрерывный список. Возвращает строгий JSON: `{ingredients: [строки как на этикетке, по порядку], confidence, is_label: bool}`. Если `is_label=false` или ингредиентов 0 (по всем фото) — ошибка «не вижу состав», лимит не списывается.
- **Фаза 2 — нормализация.** Каждая строка мапится на словарь добавок (§6): сначала точное/синонимное совпадение по нормализованной строке в Go-коде, для несматченных — один дешёвый LLM-вызов «сопоставь эти строки с кодами из списка» (передаём компактный список кандидатов). Несопоставленные строки остаются «нейтральными».
- **Фаза 3 — скоринг.** Полностью детерминированный, в Go-коде, по правилам §5. LLM в скоринге не участвует — это защита от галлюцинаций в теме здоровья.
- **Фаза 4 — объяснение.** LLM пишет короткий человеческий разбор ТОЛЬКО на основе уже посчитанных флагов и текстов-вердиктов из словаря (передаём их в промпт как единственный источник фактов). Тон: спокойный, без запугивания и без медицинских утверждений.

**Провайдер vision/LLM:** абстракция-интерфейс `LLMProvider` в Go с двумя реализациями с первого дня: Groq (multimodal Llama — биллинг уже есть под ClipsGold) и одна запасная (gpt-4o-mini класс или Claude Haiku). Выбор — env-переменной. Качество Groq-vision на русских этикетках проверяется тест-харнессом (§12) до запуска; если плохо — переключаемся флагом, не переписывая код.

**Стоимость скана:** цель < 1 ₽/скан (2 vision/LLM-вызова на дешёвых моделях, при 1 фото). При 2-3 фото в одном скане (§3, §4) стоимость растёт за счёт входных image-токенов — проверить фактическую стоимость на тест-харнессе (§12) именно на многофото-кейсах перед запуском, не только на одиночных снимках.

## 5. Скоринг v1 (детерминированный)

База: 100 баллов. Вычеты:

| Правило | Вычет |
|---|---|
| Добавка risk=3 (высокий) | −25 за каждую (макс −50 суммарно по классу) |
| Добавка risk=2 (средний) | −10 за каждую (макс −30) |
| Добавка risk=1 (низкий/спорный) | −3 за каждую (макс −9) |
| Сахар/сироп/патока в первых 3 позициях состава | −15 |
| Сахар в составе не в топ-3 | −5 |
| Маркеры трансжиров (гидрогенизированный/частично гидрогенизированный жир, маргарин) | −20 |
| Пальмовое масло | −5 |
| Соль в первых 3 позициях | −8 |

Пол: score не ниже 0. «Красные флаги» = топ-3 сработавших правила по величине вычета. Порядок ингредиентов на этикетке = порядок по убыванию массовой доли (закон о маркировке) — поэтому позиция в списке информативна.

Коэффициенты — в конфиге (таблица `scoring_rules` или yaml), не хардкод: будем тюнить после теста.

## 6. Словарь добавок

Таблица `additives`:
- `code` (E-код или slug для не-E веществ: `palm_oil`, `hydrogenated_fat`),
- `names` (массив синонимов RU: «глутамат натрия», «усилитель вкуса E621», «E621», «MSG»),
- `category` (консервант/краситель/усилитель/подсластитель/…),
- `risk` (0 нейтрально / 1 спорно / 2 средний / 3 высокий),
- `verdict_short` (1 предложение для флага),
- `verdict_full` (2–3 предложения для разбора),
- `sources_note` (внутреннее поле: на чём основана оценка).

Сид: ~250–300 E-добавок + ~20 не-E маркеров (трансжиры, сиропы, пальма). Генерируется AI-ассистентом на основе публичных классификаций (EFSA-статусы, общепринятые списки), **но**: топ-50 самых частых добавок владелец проверяет руками до запуска; спорные вещества (аспартам, нитриты, глутамат) формулируем аккуратно — «спорный/ограниченно допустимый», без слов «яд/канцероген» кроме случаев официальной классификации.

Словарь = накапливаемый ров продукта. Всё несматченное в проде логируется в `unmatched_ingredients` → еженедельно пополняем словарь.

## 7. Модель данных (Postgres)

- `users`: id, telegram_id (uniq), username, first_seen_at, free_scans_used (int), is_subscribed (bool, денормализация), created_at.
- `subscriptions`: id, user_id, provider ('stars'), status, stars_amount, started_at, expires_at, telegram_charge_id, raw_payload jsonb.
- `scans`: id, user_id, created_at, status (ok/label_not_found/error), score, flags jsonb, ingredients_raw jsonb, ingredients_matched jsonb, provider, latency_ms, cost_estimate.
- `additives`: см. §6.
- `unmatched_ingredients`: raw_text, first_seen, count.
- `events`: id, user_id, name, props jsonb, created_at (аналитика §10).

Фото: в MVP НЕ храним (только результат извлечения) — дешевле и чище по приватности. Флагом можно включить сохранение на диск для отладки.

## 8. API (Go)

- `POST /api/auth` — валидация Telegram initData (HMAC по алгоритму из доки TG), выдача короткоживущего JWT.
- `POST /api/scan` — multipart, **1-3 фото** (поле-массив, например `photos[]`; 4-е и далее — отклонить понятной ошибкой на фронте до отправки, лишнее не долетает до сервера); проверка лимита/подписки → пайплайн (все фото в одном vision-вызове, см. §4) → результат `{score, flags[], ingredients[], scans_left}`. Таймаут 30с (действует на весь запрос, не за-фото), ограничение размера каждого файла 10МБ, ресайз каждого до ~1500px по длинной стороне перед отправкой в модель.
- `GET /api/me` — лимиты, статус подписки.
- `POST /api/pay/create` — создать invoice-ссылку Stars (subscription invoice, период 30 дней).
- `POST /api/tg/webhook` — вебхук бота: `/start`, `pre_checkout_query`, `successful_payment` (создание/продление подписки).
- `GET /api/admin/stats?key=...` — счётчики за 7/30 дней: users, scans, conversions, revenue (для владельца, до нормальной админки).

Rate limit: 5 сканов/мин на пользователя. Все ошибки — человекочитаемые, на русском.

## 9. Монетизация и лимиты

- 10 бесплатных сканов навсегда на telegram_id.
- Подписка: месячная через Telegram Stars (для цифровых услуг внутри mini-app Stars обязательны по правилам платформы). Целевая цена ~249 ₽/мес → номинал в Stars выставить по актуальному курсу Stars на момент запуска (placeholder в конфиге `SUBSCRIPTION_STARS_PRICE`).
- Продление: механизм подписок Stars (Bot API subscription invoices); статус проверяем по `expires_at` + вебхук-события.
- Возвраты/споры: вручную через поддержку в личке бота (MVP).

## 10. Аналитика (события в таблицу `events`)

`app_open`, `scan_started`, `scan_ok`, `scan_label_not_found`, `paywall_shown`, `pay_started`, `pay_ok`, `sub_expired`.

Пороги решения через 30 дней после запуска:
- install→первый скан: **> 50%** (ниже — чиним онбординг);
- пейволл→оплата: **2–5%** норма, **< 1%** — плохой знак;
- CAC из посевов vs LTV (LTV на старте ≈ цена подписки × 1.5–2 в предположении медианных 1.5–2 месяцев жизни подписки — уточним по факту).

## 11. Дисклеймеры и безопасность

- В onboarding и на экране результата постоянная приписка: «Информация носит справочный характер и не является медицинской рекомендацией».
- LLM-объяснение генерится строго из словарных вердиктов (фаза 4) — модель не имеет права добавлять утверждения о здоровье от себя (зафиксировать в системном промпте + пост-проверка на запрещённые слова: «лечит», «вызывает рак» вне словарного текста и т.п.).
- Секреты только через env, fail-fast при отсутствии (RuntimeError-паттерн). Токен бота, ключи LLM-провайдеров — не в git.
- initData валидируется на каждый запрос (или JWT после /auth), иначе лимиты обходятся подделкой telegram_id.

## 12. Тест-харнесс (обязательная часть MVP)

CLI-команда `go run ./cmd/evalpipe --dir ./testdata/labels` — прогоняет папку фото этикеток через полный пайплайн, выводит таблицу: файл → извлечено ингредиентов → сматчено → score → стоимость → латентность, и суммарный отчёт. Нужна для: выбора провайдера (Groq vs запасной), контроля качества при смене промптов, оценки стоимости скана. Владелец готовит 30–50 реальных фото этикеток (разные категории: молочка, колбаса, снеки, детское, «фитнес»-продукты; разное качество съёмки).

## 13. План итераций

- **v1.0 (MVP, 2–3 недели):** всё выше.
- **v1.1 (по данным):** если конверсия в оплату ок, но частота сканов падает к 2–4 неделе → habit-слой (стрик, еженедельный «рейтинг корзины», профили аллергий/ребёнок/сахар). Если конверсия < 1% → пивот-кандидаты на том же пайплайне: косметика по составу, калории по фото тарелки.
- **v2 (при межд. платежах):** экспорт — новый словарь/язык + лендинг, код тот же.

## 14. Бэклог v1.1 (зафиксировано, не блокирует MVP)

### 14.1 Оплата через СБП-редирект (внешний лендинг)

**Почему не встроено в mini-app.** Telegram требует Stars для цифровых товаров/подписок, потребляемых строго внутри интерфейса Telegram — обходить это встроенной формой оплаты внутри самого mini-app WebView нельзя, риск блокировки платежей у бота целиком. Легальная граница: переход по `Telegram.WebApp.openLink()` на самостоятельный внешний сайт — обычная практика (запись на приём, донаты, билеты), не нарушает правила. Stars остаётся основным способом (уже реализован, одно касание внутри Telegram); СБП — второй, для тех, кто предпочитает более низкую комиссию эквайринга или у кого не работают Stars.

**Компоненты:**

1. **Лендинг** — отдельный статический/лёгкий сайт (не mini-app, не React SPA обязательно — можно простой HTML+JS), на своём поддомене (например, `pay.sedobno.ru`). Показывает: цену, кнопку/форму оплаты через провайдера.
2. **Провайдер эквайринга** — ЮKassa или CloudPayments, оба поддерживают СБП QR "из коробки" через свой SDK/API. Предпосылка: юрлицо/ИП/самозанятый уже оформлен (без этого счёт эквайринга не открыть).
3. **Привязка платежа к пользователю.** Схема:
   - Mini-app на пейволле генерирует ссылку вида `https://pay.sedobno.ru/?uid=<user_id>&sig=<HMAC>` (подпись HMAC от `user_id` с серверным секретом — защита от подмены чужого uid в URL).
   - Лендинг при инициации платежа у эквайринга передаёт `user_id` в поле `metadata`/`description` платежа (у ЮKassa есть `metadata` в create-payment API специально для таких случаев).
4. **Новая таблица `sbp_payments`** (аналог `subscriptions`, но для этого канала): `id, user_id, provider_payment_id UNIQUE, amount, status, created_at`. UNIQUE на `provider_payment_id` — та же идемпотентность, что у `telegram_charge_id`.
5. **Новый вебхук `POST /api/payments/sbp/webhook`** — принимает уведомление от эквайринга о статусе платежа. Важно: ЮKassa API v3 («Приём оплаты») **не подписывает** тело вебхука HMAC — официальная рекомендация ЮKassa — верификация по IP-адресу отправителя и повторному запросу актуального статуса объекта через API. Схема верификации: (1) IP-allowlist как defense-in-depth (диапазоны ЮKassa: `185.71.76.0/27`, `185.71.77.0/27`, `77.75.153.0/25`, `77.75.154.128/25` + IPv6, сверить в актуальной доке перед реализацией), (2) обязательный re-fetch — `GET /v3/payments/{id}` с `YOOKASSA_SECRET_KEY`, доверяем только статусу и `amount`/`metadata.user_id` из ответа API, не из тела вебхука. Структура обработки идентична `successful_payment` из §9: `INSERT ... ON CONFLICT (provider_payment_id) DO NOTHING` → если вставилась новая строка → активировать/продлить подписку в `users`/`subscriptions`, событие `pay_ok` (тот же тип события, чтобы `/api/admin/stats` считал revenue по обоим каналам вместе, с раздельной разбивкой по валюте/каналу).
6. **Ключи эквайринга живут на бэкенде (api), не на лендинге.** Лендинг остаётся тонким, без секретов: он вызывает `POST /api/payments/sbp/create` на нашем сервере, который и создаёт платёж в ЮKassa с `metadata.user_id`. Секрет ЮKassa хранится в одном месте — там же, где нужен для re-fetch в вебхуке.
7. **Env (fail-fast, по фиче-флагу):** SBP включён ⇔ задан `YOOKASSA_SHOP_ID`. Если включён — обязательны `YOOKASSA_SECRET_KEY`, `SBP_LANDING_URL`, `SBP_LINK_SECRET`(HMAC для подписи `user_id` в ссылке на лендинг, считается на бэке), `SBP_PRICE_RUB`. Если выключен — эндпоинты отдают 503, кнопка на пейволле скрыта (флаг `sbp_available` в ответе `/api/auth`/`/api/me`).

8. **UI:** на пейволле — вторая кнопка под Stars-кнопкой, нейтральная (не конкурирует визуально с основным CTA): «Оплатить картой или по СБП».

**Порядок реализации, когда возьмёмся:** сначала оформить юрлицо/самозанятого и завести аккаунт в ЮKassa (внешний процесс, не код) → лендинг (можно даже вне основного репозитория, отдельный маленький проект) → таблица + вебхук на бэке (переиспользует паттерн из §9 почти буквально) → кнопка на пейволле.

### 14.2 КБЖУ с этикетки

**Источник данных.** Не считаем сами — читаем то, что уже напечатано на упаковке (обязательное поле по ГОСТ: «Пищевая ценность на 100 г: белки/жиры/углеводы/ккал»). Задача модели та же, что для состава — извлечь текст, не вычислить.

**Решено НЕ показывать % от суточной нормы потребления** (то, что видно на некоторых этикетках, например у батончиков — «10% / 16% / 21%»), хотя технически это так же легко читается с этикетки, как граммы. Причина: в отличие от абсолютного количества (граммы, ккал — чистый факт), процент от нормы явно подставляет эталон для сравнения — человек читает это уже не как факт, а как готовый намёк «это много или мало». Это тот же полшаг к оценочному суждению о рационе конкретного человека, от которого мы сознательно уходим (см. ниже — скоринг КБЖУ не касается вообще). Дополнительная причина — непостоянство присутствия на этикетках (не все производители печатают %) при и так best-effort показе. Если после запуска увидим, что блок КБЖУ реально используется и люди хотят больше контекста — возвращаемся к вопросу с данными, не сейчас на ощупь.

**Изменение в пайплайне — только фаза 1 (извлечение), без нового LLM-вызова:**

Текущая схема ответа extract-фазы (условно):
```json
{ "is_label": true, "confidence": 0.95, "ingredients": ["сливки нормализованные", "заквасочные культуры"] }
```

Расширенная схема:
```json
{
   "is_label": true,
   "confidence": 0.95,
   "ingredients": ["сливки нормализованные", "заквасочные культуры"],
   "nutrition_per_100": {
      "protein_g": 2.5,
      "fat_g": 20.0,
      "carb_g": 3.4,
      "kcal": 203.6
   }
}
```
`nutrition_per_100` — целиком опциональное поле (может отсутствовать или быть `null`, если таблица не попала в кадр или отсутствует на упаковке). Промпт-инструкция: «если на фото также видна таблица пищевой ценности на 100 г/100 мл — извлеки её; если не видна или неполная — не выдумывай значения, оставь поле пустым». Это правило важно так же, как для ingredients — модель не должна галлюцинировать цифры.

**Скоринг это поле не трогает.** §5 (детерминированный скоринг) остаётся про качество состава (добавки, сахар, трансжиры) — КБЖУ не участвует ни в баллах, ни в цвете вердикта. Смешивать «вредность состава» и «калорийность» в одном числе было бы некорректно: калорийный продукт не обязательно плохого качества, и наоборот.

**UI — новый нейтральный блок на экране результата**, ниже IngredientList: простая табличка "на 100 г/мл" (или "на 100 мл" — брать единицу с этикетки как есть, не переводить). Без цвета, без вердикта, без слов вроде «многовато» — только факт. **Best-effort показ**: если `nutrition_per_100` пусто — блок просто не рендерится, никакой ошибки и не просим переснять (основной кадр — про состав, таблица КБЖУ может физически не попасть в кадр при съёмке "в кадре только блок Состав", как просит наш собственный онбординг — это ожидаемо, не баг).

**Модель данных.** Поле `nutrition jsonb` (nullable) в таблицу `scans` — хранить как есть для аналитики/отладки, не заводить отдельную таблицу ради четырёх чисел.

**Явно НЕ делаем (чтобы не расползалось в другой продукт):**
- Не пересчитываем на вес конкретной упаковки/порции — показываем то, что на этикетке (обычно "на 100 г").
- Не даём рекомендаций/норм ("сколько можно съесть в день") — это отдельная консультационная функция, не наш скоуп.
- Не путать с оценкой калорийности по фото готового блюда/тарелки (модель "Cal AI") — там нет печатного текста, только визуальная оценка порции на глаз, принципиально менее точная задача и по сути отдельный продукт. Не смешивать без отдельного решения о запуске второго направления.

**Порядок реализации, когда возьмёмся:** правка промпта фазы 1 + JSON-схемы ответа → миграция (добавить `nutrition jsonb` в `scans`) → проброс поля через `/api/scan` в `scanResponse` → компонент на фронте (условный рендер при наличии данных). Самая маленькая по объёму доработка из всего бэклога v1.1 — вся тяжёлая часть (vision-вызов, доставка фото, ресайз) уже существует и переиспользуется как есть.

## 15. Визуальная идентичность (финализировано)

**Разделение слоёв.** Два визуальных языка, строго не смешиваются:
- **Утилитарный слой** (экраны сканирования, лоадер, результат, ошибка) — белый фон, гротеск Golos Text, семантические цвета только в ценнике/бейджах/пейволле-CTA. Цель — скорость считывания за 2 секунды, никакой декоративности.
- **Брендовый слой** (иконка приложения, хиро-блок экрана пейволла) — приглушённая природная палитра (шалфей/индиго), бумажная зернистая текстура, ботанический линогравюрный акцент-веточка, serif Newsreader. Экраны сканирования/результата/лоадера/ошибки этот язык не используют.

**Монограмма-логотип:** курсивный Newsreader, символ — кириллическая «С» (U+0421, НЕ латинская C/U+0043). Явно зафиксировано для всех будущих генераций ассетов (сплэш, сторы, соцсети) — во избежание непреднамеренного смешения алфавитов в курсивном начертании, где С/C визуально неразличимы.

**Правило курсива:** курсив Newsreader используется только как акцент — в монограмме и логотипе. Многострочные заголовки (например, заголовок пейволла) — тем же Newsreader, но прямым начертанием: курсив на объёме текста замедляет чтение.

**Иконка приложения:** квадрат со скруглением, монограмма «С» + ботаническая веточка-акцент, два варианта фона (светлый шалфей / тёмный индиго-зелёный) под системную светлую/тёмную тему.

## 16. Системный дизайн: нагрузка, поток запроса, пороги масштабирования

**Прикидка нагрузки (сценарий успеха):** 50k активных × 3 скана/нед ≈ 21k сканов/день ≈ 0.25 rps в среднем, пик ~2.5 rps. Запрос «толстый» (5–8 с из-за LLM) → одновременных сканов на пике ≈ 20.

**Решение:** один Go-монолит, синхронный `POST /scan`, Postgres на всё. Никаких брокеров (Kafka/RabbitMQ), никакого Redis, никаких отдельных воркер-сервисов в MVP.

**Поток запроса скана:** mini-app (фото+JWT) → Caddy (TLS) → Go API: JWT → лимит (PG) → ресайз in-process → vision-вызов (LLM #1) → матчинг по словарю **в памяти процесса** (грузится при старте; перезагрузка по admin-endpoint) → детерминированный скоринг → объяснение (LLM #2) → запись scan+event (PG) → JSON. Вебхук Telegram — независимая тропа, с пайплайном не пересекается.

**Защита от перегрузки:**
- Семафор на конкурентные LLM-вызовы: env `LLM_MAX_CONCURRENT` (default 20). При исчерпании — 429 + Retry-After; фронт показывает «высокая нагрузка» и ретраит с бэкоффом.
- Таймаут запроса 30 с; таймауты на каждый LLM-вызов отдельно (12 с) с одним ретраем.
- Rate limits тарифа LLM-провайдера — единственный жёсткий потолок системы: проверить лимиты Groq-тарифа до посевов; фолбэк-провайдер переключается env-флагом.

**Данные:** события аналитики — таблица `events` в Postgres (ClickHouse не раньше ~10M событий/мес). Рост: скан ~2–4 КБ jsonb → ~20–30 ГБ/год при 20k сканов/день; один инстанс PG, партиционирование `scans` по месяцам — при необходимости, не в MVP.

**Пороги апгрейда (фиксируем заранее):**
- Устойчиво >20–30 одновременных сканов ИЛИ p95 латентности >15 с → перейти на асинхронную обработку: очередь заданий в Postgres (`SELECT ... FOR UPDATE SKIP LOCKED`), пул воркеров в том же бинарнике, фронт поллит `GET /api/scan/{id}`.
- Следующая ступень (если очередь в PG упрётся) — Redis/NATS. Kafka в этом продукте не нужна: нет множественных консьюмеров, replay и стриминговых объёмов.

# Задача: подписки v2 — автопродление + годовой тариф (Stars + ЮKassa)

## Контекст и решение владельца
Разовые 30 дней заменяем на автопродление. Stars-инвойс УЖЕ уходит
с subscription_period (расхождение с офертой было найдено ранее) — решение:
не убирать рекуррент из кода, а легализовать его в документах.
Годовой тариф вводим сразу; через Stars годовой невозможен (Bot API
поддерживает только период 30 дней) → годовой ТОЛЬКО через ЮKassa.

Тарифы:
- Месяц: 150 Stars / 249₽ (СБП/карта), автопродление
- Год: 2490₽, только СБП/карта, автопродление  [цена — решение владельца, менять здесь]

## Этап 1 — модель данных (миграция 0012 или следующий номер)
subscriptions: + plan ('monthly'|'annual'), + provider_payment_method_id
(сохранённый способ ЮKassa, nullable — у Stars его нет), + next_charge_at,
+ status ('active'|'cancelled'|'past_due'). Существующие записи → monthly.
  Продление остаётся в SQL-транзакции с SELECT FOR UPDATE (логика фикса
  денежного бага — не трогать, расширить на оба плана).

## Этап 2 — Stars (минимальные правки)
subscription_period оставить. Отмену делает юзер в настройках Telegram —
кнопку не строим, но обрабатываем вебхуки продления/отмены Stars-подписки
(successful_payment с recurring-флагами, is_recurring/is_first_recurring),
обновляем expires_at/status. Идемпотентность по telegram_charge_id (UNIQUE есть).

## Этап 3 — ЮKassa рекуррент
1. Создание платежа: save_payment_method=true, после успешного вебхука
   сохранить payment_method_id, выставить next_charge_at (+30д или +365д)
2. Планировщик: фоновая горутина в api (тикер, интервал 1ч):
   SELECT ... WHERE status='active' AND next_charge_at<=now() FOR UPDATE SKIP LOCKED
   → создать автоплатёж по сохранённому способу → по вебхуку продлить.
   Неуспех списания → status='past_due', ретрай через 24ч, после 3 неудач —
   sub_expired. Джоба идемпотентна (повторный тик не создаёт дубль платежа —
   защита через idempotence_key ЮKassa = subscription_id + период)
3. Уведомление перед списанием: за 24–48ч бот шлёт сообщение «завтра продлится,
   249₽/2490₽, отменить — в приложении». Требование к подпискам в РФ +
   режет чарджбэки. Отправку логировать (events)
4. Отмена: кнопка «Отменить подписку» в mini-app (профиль/экран подписки) →
   POST /api/sub/cancel → status='cancelled', доступ до expires_at, автосписаний
   больше нет. Подтверждение в два тапа, без удержаний и «а вы уверены»-дарков

## Этап 4 — пейволл и UI
- Пейволл: два тарифа, годовой с плашкой выгоды («2490₽ — как 10 месяцев»);
  месяц — Stars или СБП/карта, год — только СБП/карта (честно подписать)
- Экран подписки: план, дата следующего списания (subscription_expires_at
  в API уже есть, в UI не показан — закрыть этот gap здесь), способ оплаты,
  кнопка отмены
- События: pay_renewal_ok, pay_renewal_failed, sub_cancelled, renewal_notice_sent

## Этап 5 — документы и лендинг
- Оферта: автопродление обоих тарифов, порядок и срок списания, уведомление,

- Лендинг: убрать «без автопродления» отовсюду (это было selling point —
