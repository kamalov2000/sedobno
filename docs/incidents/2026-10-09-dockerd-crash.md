astra-dev ~6,5 минуты. Данные не потеряны.

## Причина — что установлено, что воспроизведено, что предположение

**Установлено по журналам сервера** (`/root/incidents/2026-10-09-dockerd-crash/`):

- dockerd 29.6.0 (containerd 2.2.5) завершился в 22:34:38 с `fatal error: concurrent map
  iteration and map write`; в стеке — buildkit: `subBuilder.EachValue` ← `loadProxyNetwork` ←
  `sharedOp.getOp/CacheMap`. Это произошло через секунду после начала `docker compose up -d
  --build` беты; в тот момент на сервере была только сессия выката беты.
- Compose беты в тот момент собирал четыре образа: один и тот же контекст `../api` трижды
  (`migrate-beta`, `seed-beta`, `api-beta`) и `web-beta`; после падения в журнале четыре
  оборванные сессии сборки.
- Перезапущенный dockerd при «Restoring containers» остановил все работавшие контейнеры и не
  запустил их снова, хотя у всех `restart: unless-stopped`. `live-restore` был выключен
  (`/etc/docker/daemon.json` отсутствовал).
- Мониторинга не было; заметили по стенду проверки примерно через 4 минуты.

**Воспроизведено вне боевого сервера** (сценарии — `ops/dockerd-crashtest/`; 09.10.2026, Docker 29.6.0 в изолированном
контейнере на машине разработки; containerd отдельно, как на сервере; dockerd перезапускает
«надзиратель» с паузой 2 с, как systemd; аварийное завершение — SIGQUIT, код 2, как при
`fatal error`):

| Сценарий | `unless-stopped` | `always` |
|---|---|---|
| аварийное завершение dockerd, live-restore выключен | остановлены и **не запущены** | перезапущен |
| штатный перезапуск dockerd (SIGTERM), live-restore выключен | перезапущены | перезапущен |
| аварийное завершение dockerd, live-restore включён | **не останавливались** | не останавливался |
| live-restore включён через SIGHUP (`systemctl reload`), затем аварийное завершение | не останавливались, перезапусков 0 | — |

Там же: с live-restore внешний трафик к опубликованному порту шёл без перерыва все 20 секунд,
пока dockerd лежал; не отвечали только обращения к `127.0.0.1` (они идут через
`docker-proxy`, который живёт вместе с dockerd). На сервере внешний трафик 80/443 идёт через
правила NAT, а не через `docker-proxy`.

Вывод о неподнявшихся контейнерах: это поведение Docker 29.6.0 при восстановлении после
**аварийного** завершения без live-restore — контейнеры с `unless-stopped` остаются
остановленными; при штатном перезапуске они поднимаются. На сервере все контейнеры —
`unless-stopped`, поэтому не поднялся ни один.

**Предположения (не доказано):**

- Что гонку в buildkit вызвали именно параллельные сборки одного контекста: падение в коде,
  объединяющем одинаковые шаги разных сборок, и четыре одновременные сессии — совпадение по
  журналу, но специально гонку не воспроизводили; в тот же вечер такие сборки несколько раз
  прошли без сбоя. Публичного описания этой ошибки не нашли; похожие ошибки Docker и buildkit
  из поиска — контекст, не подтверждение.
- Почему Docker при аварийном восстановлении считает `unless-stopped` остановленными «вручную»,
  по исходникам не разбирали — установлено поведение, а не его место в коде.

## Восстановление (если повторится)

Признак: `curl https://sedobno-pay.ru/api/health` не отвечает, `docker ps -a` показывает
`Exited` у `sostav-*`.

1. Не пересобирать и не перевыкатывать — поднять ТЕ ЖЕ контейнеры:
   ```bash
   docker start sostav-postgres-1 && sleep 5 && docker start sostav-api-1 sostav-web-1 sostav-caddy-1
   ```
2. astra-dev (его одноразовый `astra-dev-astra-migrate-1` не трогать):
   ```bash
   docker start astra-dev-astra-postgres-1 astra-dev-astra-redis-1 && sleep 5 && docker start astra-dev-astra-api-1 astra-dev-astra-worker-1 astra-dev-astra-web-1
   ```
3. Бета: `cd /opt/sostav-beta && make beta-up` (из привезённых образов, без сборки).
4. Проверить всё разом: `cd /opt/sostav && make stacks-health` — три адреса и список
   остановленных контейнеров.
5. Сохранить журналы до ротации: `journalctl --since … --until …` (всё, `-u docker`,
   `-u containerd`) в `/root/incidents/<дата>/`.
